# Phase 7: Method Registry - Context

**Gathered:** 2026-01-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Hierarchical structure for organizing detection algorithm families, versions, and configurations. Includes build-time validation of JSON-Swift parallelism and read-only registry access from dashboard. The registry organizes existing methods (like SpectralFluxMethod) and enables adding new methods without modifying core code.

</domain>

<decisions>
## Implementation Decisions

### Registry structure & metadata
- Version folders named simply: v1, v2, v3 (not semantic versioning)
- `_family.json` contains minimal metadata: name and description only
- Config files use descriptive names: `default.config.json`, `aggressive.config.json`, `conservative.config.json`
- `_index.json` is fully auto-generated by build script (no manual overrides)
- Structure: `app/methods/{family}/{version}/method.json` + `configs/*.config.json`

### Build validation rules
- JSON-Swift parallelism means: every `method.json` in every version folder requires matching Swift file in same folder
- Configs are read directly from `.config.json` files at runtime (no Swift counterpart needed)
- Validation failure causes hard build failure (not warning)
- Build script validates JSON schema correctness (not just file existence)
- Validation runs on every build (not conditional on file changes)

### Dashboard method selection
- Methods displayed as flat list with filtering (not hierarchical tree)
- Each method shows name and description only (no parameter preview)
- Dashboard persists last-used method selection in localStorage
- Selection workflow: dropdown/select method before video upload (not after)
- Dashboard reads methods directly from `app/methods/` directory (read-only access)

### Config parameter handling
- Config parameters are loosely typed in JSON (no strict type definitions in schema)
- Dashboard passes config filename to Runner (e.g., "aggressive.config.json"), not full JSON
- Runner fails the run with error if requested config file not found (no fallback to default)
- Config files must be strict JSON (no comments, no JSON5)
- Runner loads config from bundle at runtime based on filename

### Claude's Discretion
- Exact JSON schema field definitions beyond what was discussed
- Build script implementation language/tooling
- Dashboard filtering mechanism details
- Error message wording for validation failures
- _index.json format and structure

</decisions>

## Specific Ideas

- "I want the registry to feel like a simple filesystem hierarchy - family/version/config"
- Keep it simple: v1, v2, v3 versioning, not semver complexity
- Read-only from dashboard perspective - it just selects, doesn't edit

</specifics>
